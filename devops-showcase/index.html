Linting Command: ruff check app tests || true
Testing Command: pytest -v --cov=app --cov-report=term-missing
Docker Buildx: Builds researchops-api:latest & researchops-worker:latest without push
Job Dependency: docker_build has needs: test (fails fast if unit tests break)
💡 Viva Talking Point

Why do we use needs: test? To save compute time and avoid building heavy container layers if unit tests fail. Docker Buildx verifies image compilation before deployment to EC2.

name: ResearchOps AI CI/CD Pipeline

on:
  push:
    branches: [ main, master, develop ]
  pull_request:
    branches: [ main, master ]

jobs:
  test:
    name: Automated Unit & Integration Tests
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: "3.12"
          cache: "pip"
      - run: pip install -r requirements.txt pytest-cov ruff
      - run: ruff check app tests || true
      - run: pytest -v --cov=app --cov-report=term-missing

  docker_build:
    name: Container Build & Verification
    runs-on: ubuntu-latest
    needs: test
    steps:
      - uses: actions/checkout@v4
      - uses: docker/setup-buildx-action@v3
      - uses: docker/build-push-action@v5
        with:
          file: ./Dockerfile
          push: false
          tags: researchops-api:latest

⚠️ Cloud Architecture Principle

Security Group rules are explicitly defined: Port 22 and 9090 are locked down to admin CIDR, while HTTP (80/8000) and Grafana (3001) allow web traffic. All outbound traffic (0.0.0.0/0) is permitted for external API lookups.

💡 RollingUpdate Strategy: maxSurge 1 & maxUnavailable 0

During deployment, Kubernetes starts 1 new Pod first. It probes /ready. Only after the new Pod passes readiness does it terminate an old Pod. This guarantees zero downtime.

HIGH AVAILABILITY & RESILIENCE

Health Probes & Circuit Breaker Pattern

Interactive comparison of Liveness vs Readiness, and Circuit Breaker implementation protecting academic APIs from cascading failures.

Pattern CLOSED -> OPEN -> HALF-OPEN
Probe Diagnostics: Liveness vs Readiness vs Metrics
GET /health
Liveness Probe
Verifies that the ASGI Python process is responsive. If this check fails 3 times, container orchestrator triggers an immediate container restart.
GET /ready
Readiness Probe
Verifies database connection, Redis broker, and Celery workers. If downstream Postgres is offline, the container is temporarily taken out of load-balancer rotation without being killed.
GET /metrics
Prometheus Telemetry
Outputs standard Prometheus exposition text scraped every 15s for alerting and operational visibility.
💡 Classic Viva Question: Why have separate probes?

Killing a container whose database is temporarily restarting is disastrous (creates reboot storm). Readiness protects traffic routing; Liveness recovers from deadlocks.
